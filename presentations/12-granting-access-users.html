Module 12

Granting Access to Your Application Users

Amazon Cognito — sign-up, sign-in, JWTs.

📜 How Auth Evolved

  • Basic auth — username:password on every request; credentials everywhere, no revocation
  • Server-side sessions — cookie + session store; revocable, but stateful and single-origin
  • SAML — enterprise SSO across organizations; XML-heavy, browser-redirect choreography
  • OAuth 2.0 — delegated authorization: apps get scoped tokens, never your password
  • OpenID Connect — an identity layer on OAuth 2.0; signed JWTs carry who you are

Each step traded a weakness for a protocol. Cognito is a managed OIDC provider — everything below this slide builds on that last step.

🛡️ Don't Roll Your Own — Use Cognito

  • Password hashing, MFA, reset, email verification — all easy to subtly break
  • Account recovery and lockout are regulatory minefields; social IdPs need constant protocol updates
  • Use a managed identity service — Cognito, Auth0, Okta are the same category
  • Cognito is AWS's: sign-up, sign-in, reset, MFA, social login, lockout — wired directly into AWS

🧩 Cognito — Two Pieces

  • User Pool — the user directory. Stores profiles, hashes passwords, handles sign-up / sign-in, issues JWTs.
  • Identity Pool — exchanges an ID token for short-lived AWS credentials so a browser can call AWS services directly (rare; mostly for native apps).
  • Most web/API apps need only a user pool (this course does).

🎟️ What a JWT Looks Like

eyJhbGciOiJSUzI1NiIs...   header
.
eyJzdWIiOiJ1c2VyMSIs...   payload  (sub, email, exp, aud, iss)
.
MXp1ZVZ0ZGN...            signature
  • Three base64url-encoded sections joined by dots
  • Payload is readable — never put secrets in a JWT
  • Signature verifies the token wasn't tampered with

🪙 Tokens Cognito Issues

  • ID token — identity claims (sub, email, custom attrs)
  • Access token — OAuth scopes; send it when your API authorizes by scope
  • Refresh token — exchanged for new access/ID without re-login
  • Default lifetimes: ID/access 1 h, refresh 30 d (configurable per app client)
  • Our labs: a REST API Cognito authorizer with no OAuth scopes validates the ID token — that's what Labs 6b/6c send

🔑 OAuth Flow to Use

  • Authorization Code + PKCE — the right flow for SPAs and mobile
  • Client Credentials — machine-to-machine; no user
  • Avoid Implicit (deprecated) and Resource-Owner-Password (legacy)
  • SPA SDK default is SRP (USER_SRP_AUTH) — the labs enable USER_PASSWORD_AUTH only to test from the terminal
  • Managed login (formerly Hosted UI) gives you sign-up / sign-in pages out of the box

🚪 Protecting API Gateway

  • Attach a Cognito User Pool authorizer to each method
  • API GW validates signature, expiry, audience
  • Claims forwarded to Lambda via event.requestContext.authorizer.claims
  • Unauthenticated → 401; unauthorized → 403

✅ Best Practices

  • Authorization Code + PKCE for browser apps
  • Never store tokens in localStorage — in-memory or http-only cookie
  • MFA on for privileged accounts; optional for the rest
  • Turn on threat protection (formerly advanced security; Plus feature plan) for compromised-credential detection
  • Use Lambda triggers sparingly — each is a failure mode in your sign-in path
